# Validation Report

The intended authoritative validation flow is:

```powershell
scripts/run_all.ps1
```

This builds the C++ code, runs CTest, executes the benchmark, and exports reports under `reports/generated`.

## Current Software Evidence

The repository includes deterministic sample artifacts under `reports/`:

- `sample_validation_report.md`
- `sample_metrics.json`
- `sample_trace.csv`
- `sample_fault_log.json`

These are generated by `scripts/generate_report.py` for review environments without native C++ tools. They document the report format and expected validation evidence, but they are not a substitute for running the C++ build and test suite.

GitHub Actions runs the authoritative hosted validation path: default configure/build/CTest, Linux SocketCAN compilation/tests, pinned dependency-backed SOEM build/CTest, pinned FreeRTOS POSIX smoke execution, simulator/scenario/two-axis runs, benchmark and wall-clock host probe, report generation, packaging, repository health, evidence tests, and both release gates.

## Pass/Fail Gate

The project is software-complete when:

- CMake configure and build complete without compiler warnings that indicate behavioral risk.
- `emrtc_tests` passes all scenarios.
- `emrtc_benchmark` exports timing metrics and exits successfully.
- Reports contain cycle histogram, jitter, missed cycles, bus counters, recovery evidence, and scenario pass/fail table.
- Reports contain motion-performance evidence: overshoot, settling time, steady-state error, following error, two-axis path error, final two-axis position error, and explicit two-axis acceptance thresholds.
- Hardware-only work remains limited to target-specific configuration, physical commissioning, recovery, timing, motion, and stop-path evidence.
- `scripts/check_software_ready_milestone.py` passes with current version, tests, scenarios, recovery limits, execution ports, CI paths, and claim language.
